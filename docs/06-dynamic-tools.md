# 06 — 动态工具：让 Agent 的能力随工作变化

从 0.23.0 起，扩展不必为了更换工具组而重建 Agent。它可以在运行期间发布、替换或撤回自己拥有的工具，让同一个 Agent 随供应商、连接或任务变化，采用合适的工具面。

**动态的是能力供给，不是正在执行的操作快照。** 一个操作开始后，模型看到的目录和实际执行绑定保持配对；新发布的能力在下一次操作边界一起切入，不在模型与工具执行之间偷偷换实现。

静态工具仍然是默认选择。没有变化需求时，继续通过 manifest 的 `tools` 声明即可，不需要为了“动态”多包一层。

## 1. 先分清三个时刻

| 时刻 | 意义 | 不代表什么 |
| --- | --- | --- |
| 提交 | `replace` / `withdraw` 接受新的贡献状态 | 不代表当前操作已经切换工具面 |
| 采用 | 下一操作准入时，Agent 捕获目录和固定执行绑定 | 不是每次模型请求、每个 tool call 都重读目录 |
| 退役 | 旧版本不再活跃，也没有操作或未确认执行引用，核心调用它的 `retire` | 不等于提交后立即关闭旧连接 |

一次操作可以包含多个模型步骤、工具轮次和 drain 的 follow-up；这些步骤共享同一份工具快照。**follow-up 不是换面的边界。** 独立的 `compact_session` 也是一次操作，会采用当时可用的目录；但 compact 本身不执行工具。

## 2. 到底在哪里停、在哪里换？

普通替换或 Soft 撤回不会强行暂停当前操作。边界是这样的：

```text
操作 A 准入：捕获 V1 的目录与执行绑定
  ├─ 模型请求 / 工具调用 / follow-up：都使用 V1
  ├─ 扩展提交 V2：校验并记录，等待下一次准入采用
  └─ 操作 A 结束：释放对旧版本的引用

操作 B 准入：先检查前一执行是否已结算
  ├─ 捕获并安装 V2；目录、绑定、exposure 同步切换
  └─ 此后的模型请求、工具调用及 follow-up 使用 V2
```

因此，“动态前在哪一阶段停止”的准确答案是：**普通切换不截断操作 A；旧面一直服务到 A 结束，下一操作在进入模型/工具流程前完成换面。** 同一 Agent 不并发准入两个操作；繁忙时调用方得到 `Busy`，不是两个版本的执行流程相互覆盖。

首次操作略有不同：Agent 持有操作守卫完成 `on_start`，然后捕获工具面。所以扩展在 `on_start` 中完成的发布，首个操作就能使用。后续准入在首次异步等待前捕获；不能把晚到的发布承诺为“本轮立即可见”。

若前一次物理执行是否停止仍不确定，Agent 会阻止不安全的下一操作，而不是为了完成换面先关连接或假装执行已经结束。明确的执行终态或取消确认后，才可释放引用并继续。

## 3. 扩展怎样接入

### 只实现需要的部分

- 普通工具只实现 `ToolProvider::list_tools/execute`，不必实现 `tool_exposure`、Hook 或 Lifecycle。
- 只有要按操作收窄可见性时，才实现 `PipelineHook::tool_exposure`。该方法已有默认值 Direct；它表示“不额外收窄”，不会提升工具自身声明的 Deferred/Disabled。其他 Hook 回调也有默认值，例如只需要 before_tool 就只实现它。
- Lifecycle 三个阶段均有默认实现。只领取能力可只实现 on_compose；只初始化可只实现 on_start；没有自有资源清理时不用补空 on_shutdown。有资源仍需明确清理，动态版本的资源优先交给各自 retire。
- Runtime 必须转发完整 `EffectContext`，其中包含本次操作捕获的真实 provider 和调用上下文；不存在能力开关或按名字兜底的执行入口。取消必须携带 `run_id~`，与 effect id 一起定位真实调用。
- Observer 只有 `on_event(scope, event)`，Hook 的效果通知只有 `on_post_event(scope, stage)`，均默认不做事；需要通知才覆盖。DecisionPort 只实现 `evaluate(request, context~)`，调用上下文不再经兼容方法补齐。

`ToolDef` 构造器的 exposure 参数默认 Direct，可以省略；这是**构造函数参数默认值**，不是记录字段自动补齐机制。推荐通过公开构造器创建定义，不要把构造器参数可省略误解成旧完整记录字面量一定兼容。

### 发布流程

动态贡献使用已有的 `ToolProvider`，不是另一套工具执行协议：

1. 在 manifest 的 `requires` 声明 `Capability::ToolContribution`。
2. 在同步 `Lifecycle::on_compose` 中，通过 `CompositionView::tool_contributions()` 领取并保存能力句柄；未声明权限时得到 `None`。这里负责接线，不执行异步连接或发布。
3. 在 `on_start` 或后续受管理的异步流程中准备 provider，再调用 `replace(provider=..., retire=...)` 发布整组工具。
4. 检查 ACK 或错误；需要停用时调用 `withdraw()`，默认是 Soft。

句柄绑定 manifest owner，扩展只能管理自己的组。`replace` 是**整组替换**，不是追加：需要保留的工具也应包含在新组中。静态工具和其他 owner 的贡献一起参与校验；重名或非法 schema 会拒绝提交，并保留原先有效的组，不存在“后发布覆盖别人”。

每次发布只读取一次工具定义，并固定这批定义对应的 provider。不要在发布后修改同一个 provider 的行为来偷偷热换实现；需要新能力时，准备新版本并再次发布。

## 4. 三种变化，三种用途

| 动作 | 下一操作 | 已准入操作 | 适合用途 |
| --- | --- | --- | --- |
| `replace` | 采用新组 | 继续用旧版本 | MCP 重连、能力升级、连接轮换 |
| `withdraw(Soft)`，亦即默认 `withdraw()` | 不再看到该组 | 仍可使用捕获的旧版本 | 正常停用、供应商切换、平滑下线 |
| `withdraw(Hard)` | 不再看到该组 | 所有存活版本被撤销，阻止新启动，并向受影响的在飞子树发送取消 | 授权失效、紧急禁用、不允许旧能力继续使用 |

**Hard 不把新面注入当前操作。** 当前模型可能仍记得旧工具名，但后续启动会被拒绝；新的目录仍在下一操作采用。祖先被撤销的跨 owner 子调用同样受约束，无关根调用不会因为共享一个 Agent 就被一起取消。

Hard 也不是回滚或物理停止的保证：已经发生的副作用不会撤销；核心保留 provider 返回的真实结果与取消处置。`Propagated` 只表示取消信号已送达，`Stopped` 才表示执行器确认停止，仍不表示回滚。

## 5. 连接与清理：把资源交给版本，而不是交给时间猜测

给 `replace` 传入的 `retire` 负责**这次新发布版本自身的资源**，不是替换掉的旧版本。它会在这个版本将来被替换或撤回，且最后一个操作/未确认执行引用释放后调用。

例如更新 MCP 连接：

1. 准备新连接和新 provider，失败时自行释放尚未交付的资源，不破坏旧版本。
2. 发布新 provider，并附上关闭这个新连接的 `retire`。
3. 当前操作继续持有旧连接；下一操作采用新连接。
4. 旧版本没有使用者后，核心调用旧版本当初登记的清理回调。

回调必须支持重试，并避免无界等待。不要在发布 ACK 后立刻手动关闭旧连接；也不要让两个版本各自无条件关闭同一个共享连接。确需共享时，由扩展明确管理共享资源的归属。

### ACK 失败不总是提交失败

- 校验拒绝：目录没变；未被接收的新资源仍由扩展处理。
- `CleanupPending(revision, state, detail)`：**目录变化已经提交**，只是该 owner 的退役清理失败，待后续提交、操作结算或 shutdown 重试。不要当成事务回滚而盲目重发新版本。
- 成功 ACK：贡献状态已接受；不保证旧版本已经退役，也不保证当前操作已采用新面。

shutdown 开始后句柄关闭，核心负责退役流程。不要依赖在 `on_shutdown` 中重新 withdraw 来完成目录清理；如果清理失败，应处理 shutdown 错误并允许重试，而不是吞掉错误后宣布资源都关好了。

## 6. 推荐怎样利用它

### 供应商配套能力

由 provider 扩展内聚自己的搜索或 remote MCP 连接：激活时准备并发布，停用时 Soft 撤回，使用 `retire` 安全关闭旧资源。Posoco 不需要为搜索或 MCP 新增专用 Port。

**切换模型不会由核心自动触发上述流程。** 路由/供应商扩展必须自己协调模型选择与能力发布，并在下一操作准入前完成所需准备。不要在一个已准入操作中途改模型，然后期望工具快照同时随之变化。

### 按任务准备工具包

在操作边界前准备该任务需要的工具组，失败保留上一份有效能力。若只是决定工具该如何暴露，优先用 `ToolExposure` 和同步 `PipelineHook::tool_exposure` 收窄，而不是反复建立相同连接。

- `Direct`：进入模型与 compact 的工具投影。
- `Deferred`：不直接提供给模型，可供获准的工具内程序调用。
- `Disabled`：本快照内不可调用。

exposure 在操作捕获时计算，hook 只能收窄，不能提升声明权限。Hard 是当前操作中的紧急撤销手段，不要用修改 exposure 冒充即时撤权。

### 工具组合

程序工具通过真实 `ToolCallContext.tools()` / `invoke()` 发现、调用允许的目标。manifest 的 `tool_call_owners` 默认拒绝所有子调用；显式授予最小 owner 集合。子调用共享操作快照、预算和治理链，必须等待其结束，不能另建 dispatcher 绕过 schema、hook、取消与归因。`ScopedToolDispatch` 已移除。

## 7. 不要这样用

- 不要为普通固定工具引入动态贡献，增加没有收益的生命周期管理。
- 不要把 `replace` 当作当前操作中的立即热更新，也不要用 follow-up 强迫换面。
- 不要按名字执行当前“最新 provider”，绕过操作捕获的固定绑定。
- 不要为了正常换模型频繁 Hard 撤回；平滑切换优先 Soft，紧急撤权才用 Hard。
- 不要在旧操作还持有引用时关闭连接、复用已撤销版本，或用固定延时猜测退役时机。
- 不要把 `CleanupPending`、取消失败、shutdown 失败吞成成功；不要把取消信号当作停止确认。
- 不要让工具内调用脱离父作用域后台运行，或通过重入 `Agent.run_turn` 代替真实子调用。

## 8. 观察变化与迁移

`TurnEvent::ToolCatalogChanged` 提供 `Published`、`Withdrawn`、`Captured`、`CleanupFailed`。区分“提交”和“采用”：`Captured` 携带安装的 catalog version 与 operation id，**只有安装新版本才发出**，不是每操作心跳。事件没有每个工具的全部参数或连接信息，不应拿它代替执行结果。

从旧接口迁移时，注意 async replace/withdraw、ACK.state 和新的枚举分支。自定义 Runtime 必须声明支持固定绑定，并原样转发 `EffectContext`；不要通过结构字面重建上下文而丢掉绑定。详见 [Runtime 与工具调用迁移](advance/runtime.md)。
